# Virtual Patient V1

## Purpose
- Replace the finite APS demo glucose sequence with a deterministic looping virtual patient so CRT values stay alive beyond the first 20–30 seconds.

## API
- `void VirtualPatientV1_Init(void);`
- `bool VirtualPatientV1_Step(uint32_t now_s, float delivered_insulin_u_hr, virtual_patient_state_t *state);`

## State
- `epoch_s`
- `bg_mgdl`
- `meal_cob_g`
- `insulin_iob_u`
- `activity_factor`
- `basal_u_hr`
- `meal_event`
- `bolus_event`

## Scenario Phases
1. Baseline around `110 mg/dL`
2. Breakfast meal appears and COB rises
3. BG rises toward the mid/high range
4. Controller increases requested insulin
5. IOB rises from delivered insulin feedback
6. BG falls back toward target
7. Exercise window increases sensitivity and can trigger conservative safety behavior
8. Snack/recovery phase occurs before the scenario loops

## Current Loop Design
- Step cadence: `300 s` demo time per update
- Cycle length: `24` steps
- Breakfast event: step `2`, `34 g`, `180 min` absorption
- Snack event: step `14`, `18 g`, `120 min` absorption
- Exercise window: steps `17..20`
- Delivered insulin input is bounded and fed back into the next patient step

## Value Generation
- `BG` is generated from the prior BG plus bounded meal, insulin, and activity effects.
- `COB` is generated by `CobEngine`.
- `IOB` is generated by `IobEngine`.
- `INS` comes from controller output after safety processing, then feeds back into the next virtual-patient step.

## Safety / Scope
- Deterministic
- No malloc
- No real pump output
- No hardware insulin command
- Research/demo only
